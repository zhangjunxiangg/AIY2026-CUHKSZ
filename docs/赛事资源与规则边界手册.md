## 二、算力边界与通讯规则

### 2.1 明确允许

| 项目 | 规则依据 | 说明 |
|---|---|---|
| **公开 API** | 学术规则说明 - 原创性要求 | 可调用公开 API |
| **云端大模型** | 企业命题书 - M-Claw 智能体运行时 | M-Claw 本身设计为调 Kimi/Qwen API |
| **开源框架** | 学术规则说明 | ROS、OpenCV、PCL 等均可使用 |
| **模拟/降级演示** | 企业命题书 - 作品呈现要求 | "可通过合理的模拟、降级演示或流程说明呈现设计思路" |
| **多设备协同** | 企业命题书 - 分布式软总线 | 主板 + 辅助板 + 其他设备协同是官方鼓励的 |

### 2.2 没有明确禁止（灰色地带）

| 项目 | 评估 | 建议 |
|---|---|---|
| **外接算力设备**（笔记本 GPU、Jetson 等） | ⚠️ 规则未提及 | 核心感知控制尽量在板子上跑，外部设备只做辅助；路演时强调 M-Robots OS 的分布式协同价值 |
| **手机热点/自带路由器** | ✅ 可行 | 现场网络自备，规则不限制 |
| **云端训练** | ⚠️ 未提及 | 训练可以云端，但推理最好本地或说明架构 |
| **完全离线运行** | ✅ 可行 | 允许降级演示 |

### 2.3 通讯方式

| 方式 | 场景 | 说明 |
|---|---|---|
| **USB HDC** | 开发调试 | 文件推送、 shell 访问，机器人动时需拔掉 |
| **WiFi SSH** | 开发调试 + 演示 | 密钥认证（端口 2223）或密码（端口 22），已配置开机自启 |
| **WiFi HDC** | 开发调试 | `hdc tconn <IP>:5555`，需 `tmode port 5555` |
| **ROS 网络** | 多机协同 | `ROS_MASTER_URI` 指向主板，辅助板/开发机订阅话题 |
| **分布式软总线** | 多设备协同 | M-Robots OS 原生，用于设备发现、数据共享、任务流转 |
| **串口/UART** | 底层调试 | COM 口，需串口工具，不推荐现场用 |

### 2.4 关键边界推断

| 场景 | 是否可行 | 依据/风险 |
|---|---|---|
| 板子跑不动，用笔记本 GPU 推理 | ⚠️ 灰色地带 | 规则没禁止，但评分看"M-Robots OS 能力结合"（25 分），核心计算全在外部设备可能被质疑 |
| 调 Kimi/Qwen API 做高层决策 | ✅ 可行 | M-Claw 官方设计就是调云端 API |
| 完全离线 + 本地规则引擎 | ✅ 可行 | 允许降级演示 |
| 主板 + 辅助板 + 云端三级架构 | ✅ 鼓励 | 分布式软总线的典型用法 |
| 用外部传感器（如自己的相机） | ⚠️ 未提及 | 建议优先用官方提供的，避免兼容性问题 |

## 三、双板分工架构（官方设计）

| 板子 | 角色 | 负载 | 运行内容 |
|---|---|---|---|
| **主板**（机器人上） | 实时控制 + ROS Master | 高实时性 | 底盘控制、机械臂控制、Astra 相机、雷达、IMU、M-Claw、Docker |
| **辅助板**（第二块 3588S） | 视觉预处理 | 高计算 | Gemini 335 驱动、图像压缩、目标检测、RGBD 处理 |

**为什么分开？**
- 不是 USB 插槽不够，是**算力分配和系统隔离**
- 主板要保证控制实时性（100-1000Hz），不能被视觉处理拖慢
- 视觉处理崩溃不会拖垮机器人控制
- 两板通过 WiFi/网线通信（ROS 话题 `/aux_camera/*`）

## 四、备赛建议

### 4.1 算力分配策略

| 任务 | 推荐运行位置 | 理由 |
|---|---|---|
| 实时控制（底盘、机械臂） | 主板 CPU 小核 | 低延迟、确定性 |
| 传感器数据采集 | 主板 CPU 小核 | 简单 IO |
| SLAM / 路径规划 | 主板 CPU 大核 | 计算密集 |
| 目标检测 / 语义分割 | 主板 NPU 或辅助板 | 6 TOPS 专用算力 |
| 图像预处理 | 辅助板 | 不占用主板控制资源 |
| LLM / VLM 推理 | 云端 API | 8GB RAM 无法本地运行 |
| 多模态融合决策 | 主板 + M-Claw | 逻辑判断 |

### 4.2 网络准备

1. **必带**：便携路由器（GL.iNet MT3000/AXT1800 级别），板子、电脑、辅助板都连它
2. **备用**：手机热点（已验证可用）
3. **避免**：依赖会场 WiFi（不可控）

### 4.3 演示准备

1. **真跑**：核心链路尽量现场真实运行
2. **模拟**：准备脚本造数据/录屏播放作为降级
3. **兜底**：演示视频 + 设计思路讲解（规则明确允许）
4. **离线方案**：断网时本地规则引擎 + 预编程动作

### 4.4 路演话术建议

- 强调 **M-Robots OS 分布式协同**："主板管控制，辅助板管视觉，M-Claw 管决策，软总线管连接"
- 强调 **云-边协同**："本地实时控制保安全，云端大模型保智能"
- 准备 **降级演示说明**："如果网络波动，系统可自动切换到本地模式"

## 五、分布式软总线（Distributed SoftBus）实战

### 5.1 软总线是什么

分布式软总线是 OpenHarmony/M-Robots OS 的**设备间通信底座**，让多台设备像一台设备一样协同工作。在黑客松场景中，它负责：

- **设备发现**：自动发现同一网络里的其他 OpenHarmony 设备
- **数据共享**：跨设备读写文件、数据库、流数据
- **任务协同**：跨设备调用能力（如辅助板调主板的相机）
- **状态同步**：多设备间实时同步任务状态

### 5.2 板端软总线现状（实测）

| 项目 | 状态 | 说明 |
|---|---|---|
| 服务进程 | ✅ `softbus_server` 运行中 | PID 1005，开机自启 |
| 监听端口 | ✅ 38463, 36579, 43977 | 随机高端口 |
| 配置文件 | `/system/etc/communication/softbus/` | 传输权限配置 |
| Init 服务 | `/etc/init/softbus_server_musl.cfg` | 系统级自启 |
| 工具 | `softbus_tool`, `softbus_socket_tool` | 调试工具 |

### 5.3 两块板子怎么通过软总线连接

**当前官方做法（已验证）**：

```
辅助板（Gemini 335）                    主板（机器人）
┌──────────────┐                    ┌──────────────┐
│  相机驱动     │                    │  ROS Master  │
│  图像预处理   │──── WiFi/网线 ────→│  /aux_camera/*│
│  Docker 容器  │   ROS 话题订阅     │  机器人控制   │
└──────────────┘                    └──────────────┘
```

**关键：当前官方方案用的是 ROS 网络，不是软总线！**

辅助板通过 ROS 话题向主板发布数据：
```bash
# 辅助板执行
/data/gemini335/configure-car-ros.sh <主板IP>
/data/gemini335/start-gemini335.sh

# 主板订阅
rostopic echo /aux_camera/color/image_raw/compressed
```

### 5.4 软总线 vs ROS 网络

| 对比项 | 分布式软总线 | ROS 网络 |
|---|---|---|
| **设计目的** | 通用设备协同（文件、数据库、流、能力调用） | 机器人专用消息传递 |
| **协议层级** | 系统级（OpenHarmony SA） | 应用级（ROS Master） |
| **数据类型** | 文件、键值对、字节流、能力调用 | 话题/服务/动作 |
| **开发难度** | 需要 OpenHarmony 应用开发 | 标准 ROS 节点即可 |
| **当前支持** | 系统底层已运行，但上层应用未接入 | 已用于辅助相机 |
| **比赛适配** | 需额外开发 | 即插即用 |

### 5.5 比赛中怎么用软总线得分

评分标准里 **"M-Robots OS 能力结合"占 25 分**，软总线是重要组成部分。建议：

**方案 A：软总线文件共享（简单，可快速实现）**

利用软总线的分布式文件服务，让辅助板把处理结果文件直接"放"到主板上：

```python
# 辅助板：写结果到软总线共享目录
# /data/service/el1/public/dsoftbus/ 是软总线公共目录

# 主板：读取辅助板的结果
# 通过软总线挂载的分布式文件系统直接读取
```

**方案 B：软总线能力调用（进阶，展示深度）**

主板通过软总线调用辅助板的"视觉检测能力"：

```python
# 主板：声明需要视觉检测能力
# 辅助板：注册视觉检测能力到软总线
# 主板：像调本地函数一样调辅助板的检测
```

**方案 C：软总线状态同步（推荐，平衡工作量与展示效果）**

用软总线的分布式数据服务同步任务状态：

```python
# 主板发布任务状态
"task_status": "moving_to_target"

# 辅助板订阅状态，自动开始检测
# 检测到目标后回写
"target_found": true, "position": [x, y, z]
```

### 5.6 软总线开发资源

| 资源 | 位置 |
|---|---|
| 系统库 | `/system/lib64/libsoftbus_server.z.so` |
| 客户端库 | `/system/lib64/platformsdk/libsoftbus_client.z.so` |
| 权限配置 | `/system/etc/communication/softbus/softbus_trans_permission.json` |
| 调试工具 | `softbus_tool`, `softbus_socket_tool` |
| 官方文档 | M-Robots 社区 / OpenHarmony 开发者文档 |

### 5.7 实战建议

1. **如果时间紧**：先用 ROS 网络跑通辅助相机（官方已验证），路演时说"基于 M-Robots OS 分布式架构"。
2. **如果要冲高分**：在 ROS 基础上，加一层软总线文件共享或状态同步，展示"不仅用了 ROS，还用了软总线"。
3. **注意**：软总线开发需要 OpenHarmony 应用开发知识（SA、Ability、分布式数据服务等），现场 36 小时不建议深入，点到为止即可。
