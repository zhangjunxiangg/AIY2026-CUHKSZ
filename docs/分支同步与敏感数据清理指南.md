# 分支同步与敏感数据清理指南（全员版）

> 适用范围：AIY2026-CUHKSZ 仓库全体队员
> 背景：2026-08-09 main 及全部分支已做过一次历史重写（force push），目的是清除误入库的敏感数据。
> **这意味着：你电脑上的旧克隆已经失效，不要直接 `git pull`，按本文档步骤走。**
> 原则一句话：**只动自己的分支，先备份再操作，移动代替删除，不确定就问。**

---

## 0. 三条红线（先看这个）

1. **不要删任何东西。** 所有"清理"都是先复制到仓库外备份，再从 git 里豁免。任何 `rm` / `git reset --hard` / 删除分支之前，确认备份已经存在。
2. **只改自己的分支。** 不动 `main`，不动别人的分支，不重写任何历史。需要清历史（内容已经推送过）的情况，统一交给队长处理。
3. **旧克隆作废。** main 被 force push 过，旧克隆直接 pull 会把已清除的内容搅回来或产生冲突。按第一步重新同步。

---

## 1. 备份与同步（10 分钟）

```bash
# 1) 把整个旧仓库文件夹复制一份到仓库外，例如：
#    D:\backup\AIY2026-YYYYMMDD\   （Windows 直接复制文件夹即可）

# 2) 检查旧克隆里有没有未提交的改动
cd 旧仓库目录
git status
# 有改动就先提交到你自己的分支，或连文件一起复制走

# 3) 最干净的同步方式：重新克隆一份
git clone git@github.com:zhangjunxiangg/AIY2026-CUHKSZ.git AIY2026-new
cd AIY2026-new

# 4) 切到你自己的分支（你的贡献都在远端分支上，没有丢）
git checkout 你的分支名
```

- 你的代码贡献：完整保留在远端你的分支上（重写时所有分支是整体平移的，提交记录和作者信息都在）。
- 确认贡献还在：`git log --oneline 你的分支名 | head -20`，能看到自己的提交即正常。

---

## 2. 个人文档与大文件：移出仓库，留在本地

以下内容的归宿是**你自己的电脑**，不是仓库：

- 个人卡片、反思、笔记、聊天记录导出、任务管理数据
- API Key、.env、证书、SSH 密钥、任何账号密码
- 大文件：视频原件、图片素材批次、数据集、安装包（单个几十 MB 以上的一律不入库）

操作顺序（安全版）：

```bash
# 1) 先复制到仓库外
cp 要移出的文件 /d/backup/AIY2026-YYYYMMDD/

# 2) 从 git 追踪中移除（本地文件保留）
git rm --cached 文件路径

# 3) 写进 .gitignore，防止再次误提交
echo "路径/文件名" >> .gitignore

# 4) 提交这次"豁免"改动到你自己的分支
git add .gitignore
git commit -m "chore: 个人文档/大文件移出版本控制（本地保留）"
```

## 3. 敏感数据核查（每人都做一次）

在你的分支工作区里执行：

```bash
# 搜密钥特征
git grep -n "sk-" || echo "无"
git grep -niE "api[_-]?key|secret|token|password|passwd" || echo "无"

# 搜个人内容
git grep -niE "身份证|手机|密码|密钥" || echo "无"

# 看未追踪文件里有没有不该进库的东西
git status
```

处理规则：

| 情况 | 做法 |
|---|---|
| 文件在工作区、未提交 | 按第 2 节移出 + gitignore |
| 已提交到自己的分支、**未推送过** | 同上，再提交一次豁免即可 |
| **已经推送过**（内容存在于远端历史） | **不要自己重写历史！** 记录路径，报给队长统一用 filter-repo 清理 + force push |
| 不确定是不是敏感 | 默认当敏感处理：先移出，再问 |

另外：如果某个 Key 曾经以明文出现在仓库里，**清理历史不等于安全**——去对应平台作废重置才算完。

## 4. 保留你的贡献与 README 说明

合并前请确认你的分支上：

- 你的代码/模块完整，且能在最新 main 的基础上工作；
- 每个你负责的模块有 README 或文件头注释，说清楚：**它是什么、怎么用、依赖什么、注意事项**；
- 你的提交记录保留（不要 squash 成一团，贡献名单按提交作者统计）。

### 4.1 提前避免合并冲突：把自己的产出放在自己的位置

merge 冲突绝大多数来自"多人改了同一个文件"。提 PR 之前，先按下面的归置原则整理你的分支，能把冲突降到接近零：

- **代码放自己的模块目录**：`src/<你的模块>/`（如 `src/robot-control/`、`src/gemini335-web/`）。不要把自己的脚本散落在仓库根目录或别人的模块里。
- **文档放自己的主题文件/子目录**：`docs/<你的主题>.md` 或 `docs/<你的主题>/`，不要都写进同一两个共享文档。
- **素材/产物放自己的目录**（如 `presentation/assets/<批次>/`），且大文件按第 2 节豁免，不进 git。
- **共享文件能不动就不动**：根 `README.md`、`.gitignore`、共享手册是全仓库冲突最高发的三个文件。
  - 必须改 `.gitignore` 时：**只追加，不改删别人的行**；
  - 必须在共享文档里加内容时：加到自己名下的小节，并在 PR 描述里说明；
  - 根 `README` 的结构更新统一由队长做，不要各自改。
- **已经和别人撞了的文件**：merge 时保留双方内容（你的新章节 + 对方的），不确定就先问，不要用"全选我这边"覆盖。

## 5. 同步 main 并提交 PR

```bash
# 1) 把最新 main 合进你的分支（不是反过来）
git checkout 你的分支名
git merge origin/main
# 有冲突就逐个文件解决：保留双方的贡献，不确定的冲突问队长

# 2) 推送你的分支
git push origin 你的分支名

# 3) 在 GitHub 上向 main 提 Pull Request
```

PR 描述里写清楚三件事：

1. 这个分支做了什么（模块/功能/文档）；
2. 怎么验证（跑过什么测试/演示）；
3. 这次清理豁免了哪些文件（如果有）。

队长统一 review + merge。全部合并完成后，main 就是唯一主线，所有人都在 contributors 名单里。

## 附：队长 8/9 的操作过程（供参考的处理范式）

1. **先备份**：`git bundle create backup.bundle --all` 把全仓库历史打包，出问题可完整恢复；
2. **先捞回**：把历史里的个人数据恢复回本地电脑（本地保留，云端清除）；
3. **再豁免**：所有私人路径写入 `.gitignore` + `git rm --cached`（本地文件一个没删）；
4. **清历史**：`git filter-repo` 按路径清单重写全部分支（注意：同名文件可能在旧路径下还有一份，清完要全历史重新扫描验证）；
5. **重写远端**：`git push --force --all`；
6. **验证收尾**：全历史搜索密钥/密码/私人路径，确认 0 命中后才算完；
7. **善后**：泄露过的 Key 去平台作废重置；已合并 PR 的引用（refs/pull/*）无法 force push，残留需 GitHub Support 处理。

整个过程的核心心法：**备份 → 恢复本地 → 豁免 → 清历史 → 验证**，顺序不能反；本地文件一律"移动不删除"。
