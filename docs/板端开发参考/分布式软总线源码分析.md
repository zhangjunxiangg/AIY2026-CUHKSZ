## 1. 这是什么

分布式软总线是 **OpenHarmony/KaihongOS 的系统级通信组件**，不是应用层 SDK。它属于操作系统底层，为上层应用提供设备发现、组网、数据传输能力。

**核心定位**：让多台 OpenHarmony 设备像一台设备一样协同工作。

**三大能力**：
1. **发现连接**：基于 WiFi/蓝牙的设备发现
2. **设备组网**：统一组网和拓扑管理
3. **数据传输**：消息、字节、流、文件传输

## 4. 关键约束（官方 README 明确）

| 约束 | 说明 | 对比赛的影响 |
|---|---|---|
| **同一局域网** | 设备必须在同一局域网或近场 | 两块板子必须连同一个路由器/热点 |
| **先绑定再组网** | 需要安全认证/设备绑定流程 | 不是简单 socket 连接，有握手流程 |
| **主动关闭会话** | 传输完要显式 `Shutdown` | 资源管理需小心 |
| **危险权限** | `DISTRIBUTED_DATASYNC` + `DISTRIBUTED_SOFTBUS_CENTER` | 需要系统签名或 root 权限 |

## 6. 比赛可用性评估

### 6.1 为什么不建议直接用

| 问题 | 说明 |
|---|---|
| **系统级 C++ 代码** | 不是 Python/ROS 接口，需要 OpenHarmony 应用开发框架 |
| **需要 SA/Ability 框架** | 要懂 OpenHarmony 的 System Ability、Ability 生命周期 |
| **需要权限签名** | `DISTRIBUTED_DATASYNC` 是危险权限，普通应用拿不到 |
| **需要设备绑定** | 不是简单的 IP+端口连接，有安全握手流程 |
| **无高层封装** | 不像 ROS 的 `rospy.Publisher` 一行代码搞定 |

### 6.2 替代方案（推荐）

| 方案 | 难度 | 效果 | 比赛适配 |
|---|---|---|---|
| **ROS 网络** | ⭐ | 话题/服务/动作，即插即用 | ✅ 已验证可用 |
| **M-Claw delegate_task** | ⭐⭐ | 子代理任务分发 | ✅ 官方支持 |
| **HTTP/WebSocket** | ⭐ | 简单直接 | ✅ 通用 |
| **软总线（原生）** | ⭐⭐⭐⭐⭐ | 系统级分布式 | ❌ 36 小时做不完 |

### 6.3 如果一定要展示软总线

**最低成本方案**：

1. **用 `softbus_socket_tool` 命令行工具演示**
   ```bash
   # 板子自带，可以创建 socket、发送数据
   softbus_socket_tool
   ```

2. **展示软总线运行状态**
   ```bash
   ps | grep softbus_server
   netstat -tlnp | grep softbus
   ```

3. **话术包装**
   > "系统底层已启用分布式软总线，支持设备发现和组网。我们基于 ROS 网络实现应用层协同，软总线为底层通信提供支撑。"

## 8. 结论

分布式软总线是 OpenHarmony 的强大系统能力，但在 AIY 2026 黑客松 36 小时场景下：

- **不建议深入开发**：系统级 C++ + 权限签名 + 设备绑定，门槛太高
- **建议概念性展示**：展示运行状态 + 话术包装，把精力放在 ROS 应用层
- **长期学习价值**：如果对 OpenHarmony 系统开发感兴趣，这是很好的学习材料
